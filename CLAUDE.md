# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A table tennis club-night pairing app: maintain a player roster, add participants to a tournament, lock the roster and split it into rating-seeded pairs, then run live courtside scoring (race to 11 or 21, deuce/server-switch rules) and a public live/results view. React + Vite client, Express + Prisma/PostgreSQL server.

**Primary target device is the smartphone.** The scoring screen (`MatchPage`) is used courtside on a phone by a judge during a live match, and `PublicTournament`/`LiveScore` are meant to be checked on a phone by players and spectators. Every client screen is single-column and phone-first (bottom tab bar, no tables, no horizontal scrolling) — desktop is not specifically designed for, just not broken.

## Tournament flow (the whole "system")

There is no round robin / group / bracket / best-of-N system anymore — it was deliberately replaced with a Swiss-style, round-based flow. Nobody is ever eliminated between rounds.

1. **DRAFT** — anyone creates a tournament (name + table count) and automatically becomes its **manager** (`Tournament.organizerId`). Any other signed-in user can request to join (`POST /tournaments/:id/join`, creates a `TournamentUser` with `status: PENDING`); the manager approves (`POST /tournaments/:id/players/:userId/approve` → `REGISTERED`) or rejects/removes (`DELETE /tournaments/:id/players/:userId`, works on both pending and approved rows). The manager can also add already-known players directly, pre-approved (`POST /tournaments/:id/players`). Only `REGISTERED` players count toward pairing.

   **The roster is never locked.** Joining, adding and removing all keep working once the tournament is `ACTIVE` — a club night is Swiss-style and nobody is eliminated, so a latecomer simply enters the next pairing with no wins yet, and the previous "roster is locked" 400s only meant the manager had to run the evening around whoever happened to be in the room at pairing time. Only a `CANCELLED` tournament refuses new joins. Two consequences worth knowing:
   - `POST /tournaments/:id/players` **upserts**: an existing `PENDING` or `WITHDRAWN` row is promoted to `REGISTERED` rather than skipped, so re-adding someone who dropped out is the same call as adding them the first time. `POST /join` likewise turns an existing non-`REGISTERED` row back into a `PENDING` request instead of failing on the unique constraint.
   - `DELETE /tournaments/:id/players/:userId` deletes the row only while the player has played no match; afterwards it sets `status: WITHDRAWN` instead. That is what keeps the matches they already played in the standings (which read `REGISTERED` **and** `WITHDRAWN`) while taking them out of every future pairing (which reads `REGISTERED` only). `WITHDRAWN` used to be an enum value nothing ever set.
2. **Pairing / rounds** — `POST /tournaments/:id/pair` (manager only) generates the next round and flips the tournament to **ACTIVE**:
   - **Round 1** (tournament is `DRAFT`): seeds every `REGISTERED` player by `User.rating` (highest first), pairs adjacent ranks (1v2, 3v4, ...).
   - **Round 2+** (tournament already has matches): only callable once every match in the current round is `COMPLETED` (checked server-side — "Finish every match in the current round before starting a new one" otherwise). Re-ranks the same `REGISTERED` players by wins-so-far (rating breaks ties) and pairs the same way, with a best-effort pass in `generateRoundPairings` (`server/src/shared/scheduler.ts`, duplicated inline in `api/index.ts`) to avoid immediately repeating an earlier pairing.
   - **Odd headcount**: whoever has played the *most* matches so far (rating breaks ties, lowest first) sits out that round with no match and no stat change. The pick is **recorded** in `RoundBye` (one row per tournament+round, upserted by `/pair`) and comes back on `GET /tournaments/:id` as `byes`, so the round can print "sits out" next to that player. It used to be inferred client-side as "on the roster but in none of this round's matches", which also accused everyone who joined after that round of having sat it out. This must be "most", not "fewest" — picking whoever has the fewest matches played would hand the bye to the same person every round, since sitting out is exactly what keeps their count the lowest; ranking by "most played" is what actually rotates it.
   - Table numbers are assigned round-robin across `tablesCount` within each round; `Match.round` records which round a match belongs to.
3. **ACTIVE** — each `Match` is scored independently, and only by the tournament's manager (see Authorization below). The point target is an event-level default that a match can override: `Tournament.pointsToWin` (11 or 21, set at creation and settable via `PUT /tournaments/:id`) is what `/pair` stamps onto every match it creates, and the manager can still change one match with `PUT /matches/:id` while it is `NOT_STARTED`. The default exists because the choice was previously per-match only, which meant re-picking "21" on every match of an evening — and it is what makes the "11 / 21" control on the booking screen mean something. Scoring, deuce, and server-rotation logic live in `server/src/shared/scoring.ts` (`isDeuce`, `getMatchWinner`, `nextServerSide`), duplicated inline in `api/index.ts`.
   - **Matches end themselves** when a set win takes someone to `Match.setsToWin` (default 1, stamped by `/pair` from `Tournament.setsToWin`). `/end` stays as the manual override.
   - **No-shows**: `POST /matches/:id/forfeit { loserSide: 1 | 2 }` (manager only) completes a match by walkover from *any* non-`COMPLETED` state (including `NOT_STARTED`) — this exists specifically because the old `/end` endpoint only made sense on an already-started match, so a player who never showed up could leave a match stuck forever and block the round from finishing. Forfeit scores the winner `pointsToWin`–`0`.
4. **Deleting an event**: `DELETE /tournaments/:id` (manager only) removes the tournament with its matches, sets, roster and chat in one transaction, and nulls `Booking.tournamentId` on any booking that created it (the booking itself survives). Before this there was no way to remove an event at all, so every mistyped tournament — and every table booking, since each one creates an event — stayed in the public feed forever.

5. **Completion is automatic, not a button**: after any action that resolves a match to `COMPLETED` (`/score` reaching the target, `/end`, `/forfeit`), the route calls `maybeCompleteTournament(tournamentId)`, which flips `Tournament.status` to `COMPLETED` the moment no `NOT_STARTED`/`IN_PROGRESS` matches remain. This is **not final** — `POST /tournaments/:id/pair` works on a `COMPLETED` tournament too (it just checks "is there an unresolved match in the *current* round", not "is the tournament COMPLETED"), so the manager can start another round any time, which flips it back to `ACTIVE`.
6. **Event feed**: `GET /tournaments` takes optional `city` (matches `club.city`), `clubId`, `status` (comma-separated), `from`/`to` (against `startTime`) and `q` (name search) filters, **only events with `isPublic: true`**, ordered by `startTime` ascending with undated tournaments last — note this puts *finished* events first, so `Dashboard.tsx` re-splits the list client-side into upcoming/undated (ascending) and a "Past" section below it (most recent first), and offers an All/Mine toggle backed by `/tournaments/mine`. `GET /tournaments/mine` returns everything the caller organises or takes part in, each row carrying `myStatus` and `isOrganizer`.
7. Standings (`GET /tournaments/:id/standings`) are a flat win/loss/points-for/points-against table computed directly from completed matches (all rounds) among `REGISTERED` and `WITHDRAWN` players — there are no groups. `TournamentPage.tsx` groups matches by `round` (newest first) and shows a "Start round N" button gated on `canStartNextRound` (client-side mirror of the same "current round fully resolved" check).

**Visibility**: `Tournament.isPublic` (default `true`) decides whether the event appears in `GET /tournaments`. It exists because *every table booking creates an event* — without it, booking a table for a solo knockabout published it to the city feed next to a club tournament, and the only remedy was deleting it. `GET /tournaments/mine`, the event's own page, its public page and its live board ignore the flag: hiding it from the feed is not the same as making it secret. Set from the booking screen, from the manager's edit panel on `TournamentPage`, or via `PUT /tournaments/:id`.

**The city filter matches two things**, not one: events at a club in that city, *or* events with no venue whose organiser lives there (`{ OR: [{ club: { city } }, { clubId: null, organizer: { city } }] }`). `User.city` is asked for at signup and used to decide nothing at all before this; `Dashboard.tsx` also seeds its city picker from it, unless the viewer has already picked a city by hand (that choice is stored under `city` in `localStorage` and wins).

**Capacity**: `Tournament.maxPlayers` is optional. When set, it caps `REGISTERED` participants and is enforced on all three paths that can fill a roster — self-join, the manager adding players directly, and the manager approving a pending request (requests can outnumber the places, so the approve route re-checks). `PENDING` rows don't count toward it, which is what makes the "9/9 players" figure on the event feed count approved participants only (`_count: { players: { where: { status: "REGISTERED" } } }`).

**A booking always books the table _for_ something.** `POST /bookings` takes `eventType: "GAME" | "TOURNAMENT"` (plus an optional `eventTitle`, falling back to the club's name, and `pointsToWin`, which is carried onto the event as `Tournament.pointsToWin`) and creates the booking and its event in one transaction — a table held for nothing, or an event nobody has a table for, is never a state worth persisting. `Booking.gameId`/`Booking.tournamentId` record which one it made; both are nullable and `ON DELETE SET NULL`, so cancelling a booking leaves the event alone (people may already have joined) and deleting an event just detaches it. The event inherits the booking's club, table and start time (`bookingStartsAt`/`bookingEndsAt` in `server/src/shared/booking.ts` combine the stored day and "HH:MM"); a tournament also gets `endTime` from the duration. There is currently no way to book a table without creating an event.

**Booking conflicts**: `POST /bookings` refuses (409) when the requested table already has an overlapping booking that day. Overlap is computed in minutes-since-midnight (`server/src/shared/booking.ts`: `timeToMinutes`, `bookingsOverlap`, `startOfUtcDay`, duplicated inline in `api/index.ts`), and `date` is normalised to UTC midnight so "same day" doesn't depend on the submitter's timezone. A booking with no `tableId` is just a note that someone's coming, so it can never clash. `GET /clubs/:id/availability?date=` returns each table's busy intervals so the booking screen can show them before submitting.

**Rating-gated tournaments**: `Tournament.minRating`/`maxRating` are optional (set at creation in `CreateTournament.tsx`, or via `PUT /tournaments/:id`). If either is set, `POST /tournaments/:id/join` checks the caller's `User.rating` against the range and returns 403 with the range and the caller's rating in the message if they don't qualify — this is enforced only at join time, not retroactively (a player already `REGISTERED` before the range was tightened, or whose rating later drifted out of range via Elo, stays in). There's no separate "level" concept (no letter grades) — it's the same raw Elo number everywhere.

### Rating: Elo, starts at 100

`User.rating` is a persistent, global Elo rating (not scoped to one tournament) — it's what round-1 seeding and later rounds' tiebreaks sort by. New accounts default to `100` (schema default; was `300`, and `1000` before that). After a match is settled with a distinct set winner — via `/end` or `/forfeit` — `applyEloUpdate(winnerId, loserId)` (`server/src/routes/matches.ts`, mirrored inline in `api/index.ts`) updates both players' `User.rating` using standard Elo (`computeEloDelta` in `server/src/shared/scoring.ts`, K=32, loser's rating floored at 0). This happens immediately, mid-tournament — a player's rating (and therefore their seeding for the *next* round) can shift after every match, not just between tournaments.

**Only tournament matches are rated.** `applyEloUpdate` takes the event's `kind` as its first argument and returns immediately for a `GAME`. That check is the single gate that keeps games unrated — don't route around it, and don't call the Elo helper from anywhere that hasn't got the kind to hand. Elo is applied once per match, when the match is settled, based on the set tally; individual sets never move a rating.

**A match finishes itself.** `Tournament.setsToWin` / `Match.setsToWin` (default **1** — one set to 11 and the pair is done, which is what a club night actually plays) is the number of sets that takes a match; `/score` completes the match the moment a set win reaches it, and does not open another set. This is not decoration: the profile tallies, the standings and Elo all read `status: "COMPLETED"` matches **only**, so before this a match nobody remembered to end was a match that never happened — no result, no rating change, and the round could never be closed so `/pair` refused the next one. The judge's `/end` remains as a manual override for stopping early or playing on. The same goes for "bracket" and "group" features — the old `Group`/`Bracket`/`Team`/`Game` Prisma models, `BracketPage.tsx`, and the round-robin/olympic/double-elimination generators are gone.

## Three levels: event -> match -> set

Play nests three deep, and every screen and statistic reflects it:

1. **Event** — a `Tournament` row. `kind` is either `TOURNAMENT` or `GAME`; they are the *same* container (roster, rounds, pairing, standings, chat) and differ in exactly one way: a `GAME` never moves anyone's Elo. Keeping one model means one pairing engine and one standings computation instead of two that drift apart. Filter either kind with `GET /tournaments?kind=GAME` or `GET /tournaments/mine?kind=GAME`; `GamesPage.tsx` is just that filtered view, and opening a game lands on the normal `TournamentPage`.
2. **Match** — a pairing between two players within an event. A match holds a run of sets and keeps the running tally in `setsWon1`/`setsWon2`.
3. **Set** (`MatchSet`, "партия") — the thing actually played to 11 or 21 with deuce and server rotation. All point-by-point state lives here (`score1`/`score2`, `serverSide`, `letCount`, `lastScorer`/`prevServerSide`), **not** on the match.

**`setsToWin` decides when a match is over.** `/matches/:id/start` opens set 1. `/score` adds a point to the current set; when a set is won its winner is credited to the match's tally, and if that tally reaches `Match.setsToWin` the match is completed on the spot (Elo applied, no further set opened). Otherwise the next set opens immediately. The judge can still stop a match early with `/end`, and whoever won more sets takes it. An equal tally is a draw and moves nobody's rating. `/undo` reverses one point in the current set, and if that set is empty because the previous one just ended, it steps back into the previous set, reopens it and takes back the set win. `/forfeit` records a single set at the target score so a walkover still leaves consistent per-set stats.

`Match.pointsToWin` (11 or 21, settable only while `NOT_STARTED`) is the target each of its sets inherits; every set also stores its own copy so historical stats stay accurate if it ever changes. `Match.setsToWin` works the same way — stamped by `/pair` from `Tournament.setsToWin`, changeable per match while `NOT_STARTED`.

**Undo can take a completed match back.** Because the point that wins the last set now also settles the match, `/undo` on a `COMPLETED` match reopens it (`IN_PROGRESS`, `endedAt` cleared), flips the tournament back to `ACTIVE` if that match had completed it, and reverses the rating change through `Match.eloDelta` — the winner's gain is stored when it is applied so it can be handed back exactly, rather than recomputed from ratings that have since moved. Without this a mis-tap on match point would be unfixable.

**Standings** rank on matches won (on sets), then set difference, then point difference aggregated across every completed set.

### Authorization: per-tournament ownership, not global roles### Authorization: per-tournament ownership, not global roles

There is no role-gating (`ADMIN`/`ORGANIZER`/`JUDGE`) on tournament or match actions — `User.role` still exists on the schema but nothing in the tournament/match routes checks it anymore. Instead, every write action on a tournament or its matches is gated by **"are you `Tournament.organizerId`?"**:

- `server/src/routes/tournaments.ts` has a `loadOwnedTournament(res, tournamentId, userId)` helper; `server/src/routes/matches.ts` has `loadOwnedMatch(res, matchId, userId)` (fetches the match with `tournament: { select: { organizerId: true } }` and compares). Both return `null` and already sent a 404/403 response when the caller isn't the manager — every gated route does `const x = await loadOwned...(...); if (!x) return;` right after `authMiddleware`. `api/index.ts` duplicates both helpers inline (same names) since it can't import from `server/`.
- Any signed-in user can: create a tournament (becomes its manager), request to join a `DRAFT` tournament, view anything (tournament/match GETs, standings, live, public pages are unauthenticated).
- Only the tournament's manager can: approve/reject join requests, add players directly, remove players, pair, and change/start/score/undo/let/end any match in that tournament.
- Client-side mirror of this check: `TournamentPage.tsx` computes `isManager = tournament.organizerId === user?.id` and `MatchPage.tsx` computes `canManage = match.tournament?.organizerId === user?.id` (the match fetch includes `tournament.organizerId` for exactly this). These only control what UI renders — the server is the actual enforcement point, always re-check there when adding new mutations.

## Data model (`server/prisma/schema.prisma`)

`User` (login account, also the tournament participant — `Match.player1`/`player2` reference `User` directly, not a separate `Player` model; `city` is the player's home city, used by the event feed's city filter, and the free-text `club` string is only a display-level "home club" note), `Club` (a venue: `name`+`city` unique, optional `address`/`phone`, `createdById` is its manager — same "creator owns it" rule as tournaments), `ClubTable` (a table at a club: `number` unique per club, `indoor`), `Tournament` (`kind`: `TOURNAMENT` or `GAME` — see "Three levels" above; `organizerId` is its manager; `minRating`/`maxRating` optional join gate; `pointsToWin` the 11/21 target its matches are created with; `setsToWin` how many sets take a match here; `isPublic` whether it shows in the public feed; optional `clubId` venue, `startTime`/`endTime`, `description`, and `maxPlayers` capacity), `RoundBye` (who sat a given round out — `tournamentId`+`round` unique, written by `/pair`), `TournamentUser` (roster join table with `seed` — set once, at round 1, and never updated again even though standings shift — and `status: PENDING | REGISTERED | WITHDRAWN | DISQUALIFIED` — `PENDING` is a self-join request awaiting the manager's approval, `WITHDRAWN` is set when the manager drops a player who has already played (see flow step 1); `DISQUALIFIED` exists on the enum but nothing sets it), `Match` (holds `round` (which Swiss round it belongs to), `pointsToWin`, `setsToWin` (sets needed to take the match — reaching it completes the match), `eloDelta` (the rating the winner gained, so undo can reverse it), `setsWon1`/`setsWon2`, `tableNumber`, and its `sets`), `MatchSet` (one set inside a match: `index`, `pointsToWin`, `score1`/`score2`, `serverSide`, `letCount`, `lastScorer`/`prevServerSide` for undo, `winner` — this is where point-by-point state lives), `AuditLog`, `Session`, `Booking` (a table reservation — `clubId`/optional `tableId`/`date`/`startTime` ("HH:MM")/`durationHours`, owned by `userId`, plus `gameId`/`tournamentId` pointing at the event it created; **no payment processing**, it's just a record), `Subscription` ("follow a club" — `userId`+`clubId` unique pair, no billing), `ChatMessage` (per-tournament message board, `tournamentId`+`userId`+`text`).

**Undo**: each set stores `lastScorer` (which side scored last) and `prevServerSide` (server before that point) so `POST /matches/:id/undo` can reverse exactly one point deterministically. There is no multi-point undo history — one step back, within the current set, or into the previous set if the current one hasn't been played yet.

**Bookings/Subscriptions/Chat are intentionally minimal** — they exist because a reference app's design was cloned feature-for-feature *except* payments (explicitly out of scope: "оплата не нужна"). `Booking` has no price/status/payment field at all. `ChatMessage` is polled (`GET /tournaments/:id/chat` every 3s in `TournamentChatPage.tsx`), not real-time, consistent with the rest of the app (see Socket.IO note below) — access is gated to the tournament's manager or its `REGISTERED` participants (`assertCanUseChat` in `tournaments.ts`, mirrored in `api/index.ts`). Don't expand these into a real booking/payment/messaging platform without being asked — they're deliberately just enough to match the reference app's screens.

**Profile stats** (`GET /profile/stats`, `server/src/routes/profile.ts`, mirrored in `api/index.ts`) reports all three levels: `events` (how many tournaments and how many games the caller is a `REGISTERED` participant of), then, separately for `tournaments`, `games` and `total`, a `matches` tally, a `sets` tally (played/wins/losses) and `byTarget` splitting the sets into short (11) and long (21) buckets. The short/long split lives at set level because a set is the thing actually played to a target score. `ProfilePage.tsx` renders tournaments and games as two cards, since only one of them moves the rating. All of it is computed live from the database, never cached or denormalized onto `User`.

**Player profiles**: `GET /players/:id` (auth required, `server/src/routes/players.ts`, mirrored in `api/index.ts`) returns the player's public fields, their last 25 completed matches with opponent/event/sets, and a win-loss count over those matches. It backs `/player/:id` (`PlayerPage.tsx`) and the match history on `ProfilePage.tsx`. Every place a player is listed — the rating table, a roster row, a standings row, the bye line — links there; before this, tapping a player did nothing anywhere in the app.

**`/players` and `/rating` are one screen.** They used to be two components rendering the same rows with a different sort. `RatingPage.tsx` is the surviving list (rating order, search, medals for the top three, each row linking to the profile) and `PlayersPage.tsx` is a one-line re-export so the older route keeps working; the Dashboard tile points at `/rating`.

## Style conventions (client)

Dark **navy** theme (not black) with a lime-green accent — this was changed from an earlier blue/near-black palette, so don't reintroduce `#0a0a0f`/`#12121a`/`#1e1e2e`/`#3b82f6` accents if you see them in old notes or examples. Current tokens: `#0a1628` page background, `#101f36` card background, `#16283f` avatar-circle fill, `#1c3350` border/secondary surface, `#142a44`→`#0a1628` gradient (Dashboard hero card), `#ccff00` accent (buttons, active nav, badges — text is `#0a1628` on top of it for contrast), `#6b84a0`/`#93a8c2`/`#4d6480` muted text tones (light→dark), player-1/player-2 colors stay `#3b82f6`/`#ef4444` (semantic, not part of the neutral palette). `rounded-lg`/`rounded-2xl` cards, `text-xs uppercase tracking-wider` section labels, outline-style SVG icons (stroke, not fill) for nav/tiles. No emoji anywhere in UI copy or code comments.

`client/src/components/Layout.tsx` provides a fixed bottom tab bar — **5 items**: Home, Play (`/bookings`), Rating, Results, Profile (`/players` is no longer a bottom-tab destination; it's a quick-action tile on `Dashboard.tsx` instead) — plus a slim sticky top header showing the current user's `Avatar` (links to `/profile`) and a logout button. This is the app's only navigation chrome; new authenticated pages should render inside `<Layout>`. Unauthenticated/full-screen pages (`MatchPage`, `LiveScore`, `PublicTournament`, `Login`, `Register`, `TournamentChatPage`) render standalone without `Layout`.

`client/src/components/Avatar.tsx` (initials circle + a `#ccff00` rating-number badge overlapping the bottom-right corner, `size: "sm" | "md" | "lg"`) is the standard way to represent a player anywhere in the UI — used in `Layout`'s header, `PlayersPage`, `RatingPage`, `ProfilePage`, and participant/standings rows in `TournamentPage`. Reach for it instead of a bare name string when a player is shown in a list. `client/src/components/Logo.tsx` (`as: "link" | "plain"`, `size: "sm" | "lg"`) is the other shared visual atom, used in `Layout`'s header and the `Login`/`Register` hero.

**All UI copy goes through i18n** (`client/src/i18n/index.tsx`): `const { t, lang, setLang } = useT()` and `t("some.key")`, never a hard-coded string in JSX. The dictionary is a flat `key -> string` map with `ru` and `en` sides; `ru` is the default and the product language, `en` is the fallback for any key missing from `ru`. `{placeholder}` interpolation is supported (`t("tournament.round", { n: 3 })`). The chosen language persists in `localStorage` under `lang` and is switched from the card at the bottom of `ProfilePage`. Dates go through `client/src/lib/format.ts` (`formatEventDay`, `formatTimeRange`, `formatSlot`), which takes `lang` and uses `Intl` — don't format dates inline.

**Player names always carry the surname's initial**: render them through `playerName(p)` from `client/src/lib/format.ts`, which produces `"Иван П."`. Scoreboards, match rows and results used to print the bare `firstName`, which made two players with the same first name indistinguishable. Roster and participant lists that show the full `firstName lastName` are left as-is — the surname is already there. Don't inline `p.firstName` in new UI.

When adding screens, reuse the existing hex values/spacing and the terse one-line JSX style already used in `pages/*.tsx` (inline conditional rendering, no per-row sub-components) rather than introducing new patterns.

## Repo layout — two deployment targets, read this before touching backend code

This repo contains **two independent copies of the API**, kept manually in sync:

- **`server/`** — the real, modular Express app (`server/src/index.ts`, `routes/`, `middleware/`, `models/`, `socket.ts`). `routes/players.ts` (players + rating), `routes/public.ts` (`/api/live/:tournamentId` and the public tournament pages), and `routes/clubs.ts` exist so this copy serves the same surface as `api/index.ts` — before they were added, those endpoints were reachable only on the Vercel deployment. This is the source of truth for backend logic and is what runs locally (`npm run dev`) and on Render (see `render.yaml`).
- **`api/index.ts`** — a single-file duplicate of the same routes, written as one Express app exported for Vercel's serverless function runtime. It has its own inline `authMiddleware`/`requireRole`, its own copy of the scoring/standings logic, and an `/api/setup` endpoint that raw-SQL-creates tables (`CREATE TABLE IF NOT EXISTS ...`) as a substitute for running Prisma migrations on Vercel. Used only when deploying to Vercel (see `vercel.json`).

When asked to add or fix an API endpoint, mirror the change in **both** `server/src/routes/*.ts` and `api/index.ts`, and keep **both** hand-maintained SQL files in sync with `schema.prisma` if you change the schema. Neither is a real Prisma migration:

- **`server/prisma/migration.sql` — the one to run.** Additive and idempotent: it only creates tables/columns/indexes/foreign keys that are missing, each guarded by `IF NOT EXISTS` or an `EXCEPTION WHEN duplicate_object` block, so re-running it is harmless and **no data is lost**. It brings a database up to date from any earlier point. The single exception is the legacy free-text `Booking.club`/`Subscription.club` columns, which it migrates onto real `Club` rows before dropping — and that whole branch is skipped on a database that never had them. When you add a table or column, add it here as `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`.
- **`server/prisma/migration-reset.sql` — deliberate clean slate.** Drops every application table and recreates them empty. Running it always costs all existing data, so only reach for it when that is the actual intent. Add new tables/columns to its `CREATE TABLE` statements rather than appending `ALTER TABLE` sections.

After a reset, the seed (`npx tsx server/prisma/seed.ts`) is convenient for sample players but no longer required to get in: `POST /auth/register` is open self-signup in both copies. If unsure which target the user cares about, ask.

- `client/` — React 18 + Vite + Tailwind v4 + React Router SPA.

## Commands

Run from the repo root (npm workspaces: `client`, `server`).

```bash
npm run dev              # runs server (tsx watch) and client (vite) concurrently
npm run build             # builds client only (npm run build -w client)
npm run db:push           # prisma db push against server/prisma/schema.prisma
```

Per-workspace (run with `-w server` / `-w client`, or `cd` into the folder):

```bash
npm run dev -w server      # tsx watch src/index.ts (port 3000)
npm run build -w server    # tsc -> server/dist
npm run dev -w client       # vite dev server (port 5173, proxies /api and /socket.io to :3000)
npm run build -w client     # vite build -> client/dist
```

Prisma (schema lives at `server/prisma/schema.prisma`):

```bash
npx prisma generate --schema=server/prisma/schema.prisma
npx prisma db push --schema=server/prisma/schema.prisma
npx tsx server/prisma/seed.ts     # seeds admin@localhost / organizer@localhost / sample players (all password: admin123)
```

There is no test suite and no linter configured in this repo. `server/.env` holds `DATABASE_URL`/`JWT_SECRET` for local runs — it's gitignored; check it exists before assuming `npm run dev -w server` or `db:push` will work, and note that **this sandboxed environment cannot reach outbound Postgres ports (5432)** even when a valid `DATABASE_URL` is configured — `prisma db push`/`db:connect` will hang or fail here regardless of credentials. That's an environment limitation, not a schema or credentials problem; it has to be run from a machine/CI with real network egress.

### Local DB via Docker

`docker-compose.yml` brings up Postgres (`tttournament` db, `postgres`/`postgres`) plus the app itself built from the root `Dockerfile` (multi-stage: builds `server` and `client` separately, then runs `node dist/index.js` serving the compiled server with the client build copied alongside).

### Deployment

- **Vercel** (`vercel.json`): builds via `prisma generate && npm run build -w client`, serves `client/dist` as static output, rewrites `/api/*` to the `api/index.ts` serverless function.
- **Render** (`render.yaml`): builds and runs the real `server/` (`tsc` then `node server/dist/index.js`), frankfurt region, expects `DATABASE_URL` set manually in the dashboard, generates `JWT_SECRET`.

## Architecture notes

**Auth**: JWT (`jsonwebtoken`), bearer token in `Authorization` header, secret from `JWT_SECRET` env var. `server/src/middleware/auth.ts` exports `authMiddleware` (required auth) and `roleMiddleware(...roles)` (RBAC gate). **`roleMiddleware` is currently used by nothing.** `POST /auth/register` is open self-signup in *both* copies now: it takes `SelfRegisterSchema` (no `role`, no `rating` — reading either from the body would let anyone sign up as an `ADMIN`) and creates an `ORGANIZER`, which only means "can run their own events" since per-tournament ownership is what actually gates anything. It used to require an already-authenticated `ADMIN`/`ORGANIZER` in `server/`, which meant the client's Register screen answered a brand-new user with a 401 on the Render deployment while the same screen worked on Vercel. Roles: `ADMIN`, `ORGANIZER`, `JUDGE`, `PLAYER`, `VIEWER`. Passwords hashed with bcryptjs.

**Polling, and why writes fight it**: `MatchPage`/`LiveScore` poll every 2s, `TournamentPage`/`PublicTournament` every 5s. On `MatchPage` the same screen is also being written to by the judge's taps, and a poll that overlaps a `/score` call returns a board without that point — applying it visibly rolls the score back, and a judge who sees their tap undone taps again. `MatchPage` therefore guards every mutation through a `write()` wrapper that tracks in-flight writes and a generation counter: it skips polling while a write is in flight and discards any poll response whose generation changed while it was on the wire. Keep new mutations inside `write()`.

**The scoring screen follows the table, not the data model.** Players change ends after every set, so `MatchPage` puts player 1 on the left in odd sets and player 2 on the left in even ones (`leftIsP1 = shown.index % 2 === 1`), moving the score columns, the `+1` buttons and the walkover buttons together, with an "ends swapped" line under the board. The colours do **not** move: blue is always player 1 and red always player 2, so identity stays readable while position matches reality. Matches close themselves at `setsToWin`, so the "end this match" prompt is only for the two cases that still need one: a match left hanging from before that existed (its target is already met yet it is still open), and one the judge chose to play on past a two-set lead.

**Destructive actions confirm in-place**: ending a match, a walkover and deleting a tournament all settle something that cannot be undone (`/end` and `/forfeit` also move Elo), and on a phone held courtside they sit a thumb's width from the scoring buttons. Each renders an inline confirm panel rather than firing on the first tap — no `window.confirm`, same navy/lime styling as everything else.

**Real-time updates**: `server/src/socket.ts` sets up a full Socket.IO server (`join-tournament`, `join-match`, `score-update`, `match-end`, `game-update` events), initialized in `server/src/index.ts`. The **client does not use Socket.IO** — `client/src/context/SocketContext.tsx` (despite the filename) implements a `PollingProvider`/`usePoll` hook, and `MatchPage`/`LiveScore` poll their REST endpoints on a 2s interval instead. Treat the server's Socket.IO layer as unused by the current client unless wiring up real socket consumption.

**Client routing** (`client/src/App.tsx`): most routes are behind `RequireAuth` (redirects to `/login` if no token in `AuthContext`). `/public/tournament/:id` and `/live/:tournamentId` are intentionally public/unauthenticated. `client/src/services/api.ts` centralizes all REST calls through an `apiService` object backed by an axios instance that auto-attaches the JWT from `localStorage`.

**Validation**: Zod schemas for request bodies live in `server/src/shared/schemas.ts` (used by `server/src/routes/*`) — the top-level `shared/schemas.ts` package is a separate, unused leftover (see dead-code note above).
