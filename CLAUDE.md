# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A table tennis club-night pairing app: maintain a player roster, add participants to a tournament, split it into rating-seeded pairs, then run live courtside scoring (the judge records who took each set) and a public live/results view. React + Vite client, Express + Prisma/PostgreSQL server.

**Primary target device is the smartphone.** The scoring screen (`MatchPage`) is used courtside on a phone by a judge during a live match, and `PublicTournament`/`LiveScore` are meant to be checked on a phone by players and spectators. Every client screen is single-column and phone-first (bottom tab bar, no tables, no horizontal scrolling) — desktop is not specifically designed for, just not broken.

## Tournament flow (the whole "system")

There is no round robin / group / bracket / best-of-N system anymore — it was deliberately replaced with a Swiss-style, round-based flow. Nobody is ever eliminated between rounds.

1. **DRAFT** — anyone creates a tournament (name + table count) and automatically becomes its **manager** (`Tournament.organizerId`). Any other signed-in user can request to join (`POST /tournaments/:id/join`, creates a `TournamentUser` with `status: PENDING`); the manager approves (`POST /tournaments/:id/players/:userId/approve` → `REGISTERED`) or rejects/removes (`DELETE /tournaments/:id/players/:userId`, works on both pending and approved rows). The manager can also add already-known players directly, pre-approved (`POST /tournaments/:id/players`). Only `REGISTERED` players count toward pairing.

   **The roster is never locked.** Joining, adding and removing all keep working once the tournament is `ACTIVE` — a club night is Swiss-style and nobody is eliminated, so a latecomer simply enters the next pairing with no wins yet, and the previous "roster is locked" 400s only meant the manager had to run the evening around whoever happened to be in the room at pairing time. Only a `CANCELLED` tournament refuses new joins. Two consequences worth knowing:
   - `POST /tournaments/:id/players` **upserts**: an existing `PENDING` or `WITHDRAWN` row is promoted to `REGISTERED` rather than skipped, so re-adding someone who dropped out is the same call as adding them the first time. `POST /join` likewise turns an existing non-`REGISTERED` row back into a `PENDING` request instead of failing on the unique constraint.
   - `DELETE /tournaments/:id/players/:userId` deletes the row only while the player has played no match; afterwards it sets `status: WITHDRAWN` instead. That is what keeps the matches they already played in the standings (which read `REGISTERED` **and** `WITHDRAWN`) while taking them out of every future pairing (which reads `REGISTERED` only). `WITHDRAWN` used to be an enum value nothing ever set.
2. **Pairing / rounds** — `POST /tournaments/:id/pair` (manager only) generates the next round and flips the tournament to **ACTIVE**:
   - **Round 1** (tournament is `DRAFT`): seeds every `REGISTERED` player by the manager's manual seeding if set, otherwise by `User.rating` (highest first), and pairs adjacent ranks (1v2, 3v4, ...). Manual seeding is `PUT /tournaments/:id/seeding { userIds }` (manager, DRAFT only, the full order of approved players) — it exists because everyone starts at 100, so a strong newcomer would otherwise be seeded last. `TournamentPage` shows up/down arrows on the roster in DRAFT. Seeded players come first, anyone approved later follows by rating.
   - **Round 2+** (tournament already has matches): only callable once every match in the current round is `COMPLETED` (checked server-side — "Finish every match in the current round before starting a new one" otherwise). Re-ranks the same `REGISTERED` players by wins-so-far (rating breaks ties) and pairs the same way, with a best-effort pass in `generateRoundPairings` (`server/src/shared/scheduler.ts`) to avoid immediately repeating an earlier pairing.
   - **Odd headcount**: whoever has played the *most* matches so far (rating breaks ties, lowest first) sits out that round with no match and no stat change. The pick is **recorded** in `RoundBye` (one row per tournament+round, upserted by `/pair`) and comes back on `GET /tournaments/:id` as `byes`, so the round can print "sits out" next to that player. It used to be inferred client-side as "on the roster but in none of this round's matches", which also accused everyone who joined after that round of having sat it out. This must be "most", not "fewest" — picking whoever has the fewest matches played would hand the bye to the same person every round, since sitting out is exactly what keeps their count the lowest; ranking by "most played" is what actually rotates it.
   - Table numbers are assigned round-robin across `tablesCount` within each round; `Match.round` records which round a match belongs to.
3. **ACTIVE** — each `Match` is scored independently, by **either of its two players or the tournament's manager** (see Authorization below) — at a club night with several tables the manager cannot stand at every one, so the players at the table enter their own sets, the way a paper score sheet works. **The unit of scoring is the set, not the point**: `POST /matches/:id/score { side }` records one whole set for that side. Nothing tracks the rally-by-rally score, so there is no deuce, no service rotation and no target score to reach. `Tournament.setsToWin` / `Match.setsToWin` is how many sets the match is *played to*, but it is a prompt, not a cap — the pair can play more, and nothing ends on its own.
   - **A match is settled by the judge**, with `/end` (or `/forfeit`). This matters: the profile tallies, the standings and the rating all read `status: "COMPLETED"` matches **only**, so an unfinished match counts nowhere and its round cannot be closed. `MatchPage` therefore makes "Завершить" the primary action rather than a footnote, and highlights it once `setsToWin` is reached.
   - **Settling writes the rating first**: `finishMatch` moves the rating (`applyRatingUpdate`: single-statement writes, no `$transaction` — the pooled Postgres drops multi-statement transactions) and only then marks the match `COMPLETED` in one write that also carries `eloDelta`; it reverts the rating if that write fails. The old order (COMPLETED first, Elo after) left a settled match with no points whenever the Elo write failed, and the judge stuck on the scoreboard with an error. Once the match is settled, housekeeping failures are logged, never returned. `MatchPage` also checks the match after a failed `/end` and leaves for the event if it is in fact `COMPLETED`.
   - **Reaching `setsToWin` lights up "Завершить" and says the match can be settled — and that playing on is fine**, every set still counts. Ending earlier is allowed but asks with a different confirm text.
   - **No draws**: table tennis has none, so `/end` refuses an equal set tally (and a match with no sets) with a 400 — the pair plays a deciding set. `checkCanEnd` in `server/src/shared/scoring.ts`; `MatchPage` disables "Завершить" with the reason.
   - **No-shows**: `POST /matches/:id/forfeit { loserSide: 1 | 2 }` (manager only, and **unrated**: `finishMatch(match, rated = false)` — a no-show says nothing about how either player plays, so a walkover moves nobody's Elo) completes a match by walkover from *any* non-`COMPLETED` state (including `NOT_STARTED`) — this exists specifically because the old `/end` endpoint only made sense on an already-started match, so a player who never showed up could leave a match stuck forever and block the round from finishing. A walkover records a single set for whoever turned up.
4. **Deleting an event**: `DELETE /tournaments/:id` (manager only) removes the tournament with its matches, sets, roster and chat in one transaction, and nulls `Booking.tournamentId` on any booking that created it (the booking itself survives). Before this there was no way to remove an event at all, so every mistyped tournament — and every table booking, since each one creates an event — stayed in the public feed forever.

5. **Completion is automatic, not a button**: after any action that resolves a match to `COMPLETED` (`/score` reaching the target, `/end`, `/forfeit`), the route calls `maybeCompleteTournament(tournamentId)`, which flips `Tournament.status` to `COMPLETED` the moment no `NOT_STARTED`/`IN_PROGRESS` matches remain. This is **not final** — `POST /tournaments/:id/pair` works on a `COMPLETED` tournament too (it just checks "is there an unresolved match in the *current* round", not "is the tournament COMPLETED"), so the manager can start another round any time, which flips it back to `ACTIVE`.
6. **Event feed**: `GET /tournaments` takes optional `city` (matches `club.city`), `clubId`, `status` (comma-separated), `from`/`to` (against `startTime`) and `q` (name search) filters, **only events with `isPublic: true`**, ordered by `startTime` ascending with undated tournaments last — note this puts *finished* events first, so `Dashboard.tsx` re-splits the list client-side into upcoming/undated (ascending) and a "Past" section below it (most recent first), and offers an All/Mine toggle backed by `/tournaments/mine`. `GET /tournaments/mine` returns everything the caller organises or takes part in, each row carrying `myStatus` and `isOrganizer`.
7. Standings (`GET /tournaments/:id/standings`, `computeStandings` in `server/src/shared/standings.ts`) rank on matches won, then **Buchholz** (the sum of every opponent's wins — the usual Swiss tiebreak, returned as `buchholz`), then set difference, computed directly from completed matches (all rounds) among `REGISTERED` and `WITHDRAWN` players — there are no groups. `TournamentPage.tsx` groups matches by `round` (newest first) and shows a "Start round N" button gated on `canStartNextRound` (client-side mirror of the same "current round fully resolved" check).

**Quick game**: `POST /tournaments/quick-game { opponentId, setsWon1, setsWon2, clubId?, name? }` records a friendly game already played in one call — a `GAME` created `COMPLETED`, `isPublic: false`, both players `REGISTERED`, one completed match with its set rows. Two people who just played don't want an event with rounds; it is the "Записать результат" form on `GamesPage`. Unrated like every `GAME`, and it shows up in both players' history and stats.

**Participant view**: `GET /matches/mine` (auth) returns the caller's `NOT_STARTED`/`IN_PROGRESS` matches in `ACTIVE` events; `Dashboard` renders each as a "Твой матч" card above the hero (polled every 10s, skipped for guests). `TournamentPage` puts the same card on top (opponent, table, score, link) or "ты отдыхаешь" on a bye, shows the manager which matches the round is still waiting on under the disabled "next round" button, and flashes a notice (plus `navigator.vibrate`) when a poll brings in a new round.

**Visibility**: `Tournament.isPublic` (default `true`) decides whether the event appears in `GET /tournaments`. It exists because *every table booking creates an event* — without it, booking a table for a solo knockabout published it to the city feed next to a club tournament, and the only remedy was deleting it. `GET /tournaments/mine`, the event's own page, its public page and its live board ignore the flag: hiding it from the feed is not the same as making it secret. Set from the booking screen, from the manager's edit panel on `TournamentPage`, or via `PUT /tournaments/:id`.

**The city filter matches two things**, not one: events at a club in that city, *or* events with no venue whose organiser lives there (`{ OR: [{ club: { city } }, { clubId: null, organizer: { city } }] }`). `User.city` is asked for at signup and used to decide nothing at all before this; `Dashboard.tsx` also seeds its city picker from it, unless the viewer has already picked a city by hand (that choice is stored under `city` in `localStorage` and wins).

**Capacity**: `Tournament.maxPlayers` is optional. When set, it caps `REGISTERED` participants and is enforced on all three paths that can fill a roster — self-join, the manager adding players directly, and the manager approving a pending request (requests can outnumber the places, so the approve route re-checks). `PENDING` rows don't count toward it, which is what makes the "9/9 players" figure on the event feed count approved participants only (`_count: { players: { where: { status: "REGISTERED" } } }`).

**A booking always books the table _for_ something.** `POST /bookings` takes `eventType: "GAME" | "TOURNAMENT"` (plus an optional `eventTitle`, falling back to the club's name, and `setsToWin`, which is carried onto the event as `Tournament.setsToWin`) and creates the booking and its event in one transaction — a table held for nothing, or an event nobody has a table for, is never a state worth persisting. `Booking.gameId`/`Booking.tournamentId` record which one it made; both are nullable and `ON DELETE SET NULL`, so cancelling a booking leaves the event alone (people may already have joined) and deleting an event just detaches it. The event inherits the booking's club, table and start time (`bookingStartsAt`/`bookingEndsAt` in `server/src/shared/booking.ts` combine the stored day and "HH:MM"); a tournament also gets `endTime` from the duration. There is currently no way to book a table without creating an event.

**Booking conflicts**: `POST /bookings` refuses (409) when the requested table already has an overlapping booking that day. Overlap is computed in minutes-since-midnight (`server/src/shared/booking.ts`: `timeToMinutes`, `bookingsOverlap`, `startOfUtcDay`), and `date` is normalised to UTC midnight so "same day" doesn't depend on the submitter's timezone. A booking with no `tableId` is just a note that someone's coming, so it can never clash. `GET /clubs/:id/availability?date=` returns each table's busy intervals so the booking screen can show them before submitting.

**Rating-gated tournaments**: `Tournament.minRating`/`maxRating` are optional (set at creation in `CreateTournament.tsx`, or via `PUT /tournaments/:id`). If either is set, `POST /tournaments/:id/join` checks the caller's `User.rating` against the range and returns 403 with the range and the caller's rating in the message if they don't qualify — this is enforced only at join time, not retroactively (a player already `REGISTERED` before the range was tightened, or whose rating later drifted out of range via Elo, stays in). There's no separate "level" concept (no letter grades) — it's the same raw Elo number everywhere.

### Rating: FNTR formula, starts at 100

`User.rating` is a persistent, global rating (not scoped to one tournament) — it's what round-1 seeding and later rounds' tiebreaks sort by. It is a `Float`, because the Russian Table Tennis Federation (ФНТР) formula pays fractional points. New accounts default to `100`. It used to be Elo (K=32); the switch replaced `computeEloDelta` with `computeFntrDelta` in `server/src/shared/scoring.ts`:

- winner gains `(100 - (Rw - Rl)) / 10 * KT`; the loser gives up **half** of that. Rw/Rl are the two ratings, KT the tournament's coefficient.
- if the winner is more than **100** points above the loser (`Rw - Rl > 100`) both deltas are 0. Without that cut-off the formula goes negative and the winner would lose points.
- it is **not zero-sum**, so the loser's change is stored on its own: `Match.eloDelta` is the winner's gain, `Match.eloDeltaLoser` the loser's (<= 0, as actually applied, i.e. after the floor at 0). Every consumer that used to negate `eloDelta` for the loser (`standings.ts`, `stats.ts`, `matchDelta` in `client/src/lib/format.ts`) reads `eloDeltaLoser` instead — do not reintroduce `-eloDelta`. The column names predate FNTR and were kept to avoid a rename migration.
- values are kept to two decimals (`round2`); the client shows a rating with one decimal only when it has one (`formatRating`) and a delta with up to two (`formatDelta`).

**KT** is `Tournament.ratingWeight`, 0.1–1, default 0.5 (FNTR's default), set by the manager in `CreateTournament.tsx` and the edit panel of `TournamentPage`, and accepted by `POST`/`PUT /tournaments`. Ignored for a `GAME`.

**Which rating goes into the formula is the rating at the start of the tournament**, not the current one: FNTR has a player start each competition with the rating from the last tournament played, and rates all of a tournament's matches against those. `TournamentUser.ratingStart` holds it; `applyRatingUpdate` (`server/src/routes/matches.ts`) writes it the first time a player's match in that event is settled (nothing in the event can have moved their rating before that) and reads it afterwards. The change is still added to `User.rating` immediately, so the profile and the rating list are current the moment a match is settled — only the *inputs* are pinned. Consequently the ratings that shape the next round's seeding are current ones, but the points a match is worth do not depend on how earlier rounds went. A player added after round 1 gets their `ratingStart` at their own first settled match.

After a match is settled with a distinct set winner — via `/end` — `applyRatingUpdate(tournament, winnerId, loserId)` moves both players' `User.rating` (loser floored at 0). `/forfeit` is unrated (see above).

**Only tournament matches are rated.** `applyRatingUpdate` takes the event (`kind`, `ratingWeight`) and returns immediately for a `GAME`. That check is the single gate that keeps games unrated — don't route around it, and don't call the delta helper from anywhere that hasn't got the kind to hand. The rating is applied once per match, when the match is settled, based on the set tally; individual sets never move a rating.

**Recalculating existing ratings**: `server/prisma/recalc-fntr.sql`, run by hand after `migration.sql` (it refuses to run without the new columns). It is a single `DO` block, so it works through the pooler and applies all or nothing; as shipped it is a **dry run** that prints the new ratings as `NOTICE`s, and setting `apply_changes` to `true` writes. It replays every rated match (completed, `TOURNAMENT` kind, distinct winner, with an `eloDelta` — the old code only wrote one for a rated result) in `endedAt` order from 100 (demo accounts from their first match snapshot) and rewrites `User.rating`, both deltas, `rating1Before/2Before` and `ratingStart`. Matches with a winner but no `eloDelta` (walkovers, or older than the column) are counted and left out. It is idempotent. **The formula now lives in two places**, `computeFntrDelta` and this file — change both; the SQL rounds on exact decimals and the TS on floats, so a value on a half-cent boundary can differ by 0.01. Tested on a throwaway Postgres 17 against a TS version of the same replay (since removed) with identical output; never run against the real database from here.

Things about the FNTR rules the sources did not settle, and that the app therefore decides itself: the starting rating (100), whether a walkover is rated (it is not), and the floor at 0. The official Положение was not consulted, only the formulas published on ttsport.ru / ttw.ru.

**Points are not played out** — there is no rally-by-rally scoreboard, deuce handling or service rotation, and asking for one is a new feature. A set may *optionally* carry its final rally score for the record: `/score { side, score1?, score2? }` stores it in `MatchSet.score1`/`score2` (both or neither, must agree with `side`, 0:0 means "not entered"; `checkSetScore`). Nothing derives the winner from it. The other old columns (`serverSide`/`lastScorer`/`prevServerSide`/`letCount`, and `pointsToWin` on `Tournament`/`Match`/`MatchSet`) are still in the database but not mapped and nothing reads them. The same goes for "bracket" and "group" features — the old `Group`/`Bracket`/`Team`/`Game` Prisma models, `BracketPage.tsx`, and the round-robin/olympic/double-elimination generators are gone.

## Three levels: event -> match -> set

Play nests three deep, and every screen and statistic reflects it:

1. **Event** — a `Tournament` row. `kind` is either `TOURNAMENT` or `GAME`; they are the *same* container (roster, rounds, pairing, standings, chat) and differ in exactly one way: a `GAME` never moves anyone's rating. Keeping one model means one pairing engine and one standings computation instead of two that drift apart. Filter either kind with `GET /tournaments?kind=GAME` or `GET /tournaments/mine?kind=GAME`; `GamesPage.tsx` is just that filtered view, and opening a game lands on the normal `TournamentPage`.
2. **Match** — a pairing between two players within an event. A match holds a run of sets and keeps the running tally in `setsWon1`/`setsWon2`.
3. **Set** (`MatchSet`, "партия") — the unit of scoring. A set row records only `index` and `winner`: who took it, and nothing else.

**A set is recorded, not played out.** `/matches/:id/start` just opens the match — no set is created up front. `/score { side }` appends one `MatchSet` (`index`, `winner`, `status: COMPLETED`) and increments that side's tally; there is no point-by-point state to keep, so a set row's `winner` is its whole content. `/undo` deletes the last set row and decrements the tally — one step, no deeper history. `/forfeit` records a single set for whoever turned up. Nothing finishes a match automatically: `/end` settles it and whoever won more sets takes it; an equal tally cannot be ended.

`Match.setsToWin` (default **3**, the usual club format) is stamped by `/pair` from `Tournament.setsToWin` and can be changed per match while it is `NOT_STARTED` — by the manager or either player; the table number and judge stay the manager's. Every setsToWin input in the client is `components/SetsToWinPicker.tsx` (2/3/4 presets plus -/+). **It is not capped** — any number ≥ 1 — because how many sets a pair play is their business; it only drives the "this match can be ended" prompt.

**Undo can take a completed match back** — manager only (players get a 403; `MatchPage` shows the manager a "Вернуть матч в игру" button on a finished match). `/undo` on a `COMPLETED` match reopens it (`IN_PROGRESS`, `endedAt` cleared), flips the tournament back to `ACTIVE` if that match had completed it, and reverses the rating change through `Match.eloDelta`/`eloDeltaLoser` — both changes are stored when they are applied so they can be handed back exactly, rather than recomputed from ratings that have since moved. Without this a match ended by mistake would be unfixable.

**Standings** rank on matches won, then set difference. There is no points-for/against column any more: the rally-by-rally score is not recorded, so sets are all there is to aggregate.

### Authorization: per-tournament ownership, not global roles### Authorization: per-tournament ownership, not global roles

There is no role-gating (`ADMIN`/`ORGANIZER`/`JUDGE`) on tournament or match actions — `User.role` still exists on the schema but nothing in the tournament/match routes checks it anymore. Instead, every write action on a tournament or its matches is gated by **"are you `Tournament.organizerId`?"**:

- `server/src/routes/tournaments.ts` has a `loadOwnedTournament(res, tournamentId, userId)` helper; `server/src/routes/matches.ts` has `loadOwnedMatch(res, matchId, userId)` (fetches the match with `tournament: { select: { organizerId: true } }` and compares). Both return `null` and already sent a 404/403 response when the caller isn't the manager — every gated route does `const x = await loadOwned...(...); if (!x) return;` right after `authMiddleware`.
- Any signed-in user can: create a tournament (becomes its manager), request to join a `DRAFT` tournament, view anything (tournament/match GETs, standings, live, public pages are unauthenticated).
- Only the tournament's manager can: approve/reject join requests, add players directly, remove players, set seeding, pair, record a walkover, reopen a finished match, and change a match's table/judge.
- The manager **or either player of that match** can: set its setsToWin before start, start it, record sets, undo the last set of an unfinished match, and end it. `loadScorableMatch` in `matches.ts` returns the match plus `isManager`; routes that need the manager check that flag. `/start` refuses a `COMPLETED` match, since it would reopen it without handing the rating back.
- Client-side mirror of this check: `TournamentPage.tsx` computes `isManager = tournament.organizerId === user?.id` and `MatchPage.tsx` computes `isManager` the same way and `canScore = isManager || user is player1/player2` (the match fetch includes `tournament.organizerId` for exactly this). These only control what UI renders — the server is the actual enforcement point, always re-check there when adding new mutations.

## Data model (`server/prisma/schema.prisma`)

`User` (login account, also the tournament participant — `Match.player1`/`player2` reference `User` directly, not a separate `Player` model; `city` is the player's home city, used by the event feed's city filter, and the free-text `club` string is only a display-level "home club" note), `Club` (a venue: `name`+`city` unique, optional `address`/`phone`, `createdById` is its manager — same "creator owns it" rule as tournaments), `ClubTable` (a table at a club: `number` unique per club, `indoor`), `Tournament` (`kind`: `TOURNAMENT` or `GAME` — see "Three levels" above; `organizerId` is its manager; `minRating`/`maxRating` optional join gate; `setsToWin` how many sets its matches are played to; `isPublic` whether it shows in the public feed; optional `clubId` venue, `startTime`/`endTime`, `description`, and `maxPlayers` capacity), `RoundBye` (who sat a given round out — `tournamentId`+`round` unique, written by `/pair`), `TournamentUser` (roster join table with `seed` — set once, at round 1, and never updated again even though standings shift — and `status: PENDING | REGISTERED | WITHDRAWN | DISQUALIFIED` — `PENDING` is a self-join request awaiting the manager's approval, `WITHDRAWN` is set when the manager drops a player who has already played (see flow step 1); `DISQUALIFIED` exists on the enum but nothing sets it), `Match` (holds `round` (which Swiss round it belongs to), `setsToWin` (how many sets it is played to — a prompt, not a cap), `eloDelta` (the rating the winner gained, so undo can reverse it), `setsWon1`/`setsWon2`, `tableNumber`, and its `sets`), `MatchSet` (one set inside a match: `index`, `winner`, `status` — a set records who took it and nothing else), `AuditLog`, `Session`, `Booking` (a table reservation — `clubId`/optional `tableId`/`date`/`startTime` ("HH:MM")/`durationHours`, owned by `userId`, plus `gameId`/`tournamentId` pointing at the event it created; **no payment processing**, it's just a record), `Subscription` ("follow a club" — `userId`+`clubId` unique pair, no billing), `ChatMessage` (per-tournament message board, `tournamentId`+`userId`+`text`).

**Undo**: `POST /matches/:id/undo` deletes the last `MatchSet` row and decrements that side's tally. One step back, no deeper history. On a `COMPLETED` match it also reopens the match and reverses the rating (see above).

**Bookings/Subscriptions/Chat are intentionally minimal** — they exist because a reference app's design was cloned feature-for-feature *except* payments (explicitly out of scope: "оплата не нужна"). `Booking` has no price/status/payment field at all. `ChatMessage` is polled (`GET /tournaments/:id/chat` every 3s in `TournamentChatPage.tsx`), not real-time, consistent with the rest of the app (see Socket.IO note below) — access is gated to the tournament's manager or its `REGISTERED` participants (`assertCanUseChat` in `tournaments.ts`). Don't expand these into a real booking/payment/messaging platform without being asked — they're deliberately just enough to match the reference app's screens.

**Profile stats** (`GET /profile/stats`, `server/src/routes/profile.ts`) reports all three levels: `events` (how many tournaments and how many games the caller is a `REGISTERED` participant of), then, separately for `tournaments`, `games` and `total`, a `matches` tally and a `sets` tally (played/wins/losses) taken straight off the matches' set counters. There is no split by target score — no score is recorded to split by. `ProfilePage.tsx` renders tournaments and games as two cards, since only one of them moves the rating. All of it is computed live from the database, never cached or denormalized onto `User`.

**Results and statistics** (`server/src/routes/stats.ts` + pure logic in `server/src/shared/stats.ts`; all unauthenticated, public player shape):
- `GET /results?kind=&city=&q=&userId=` — `ACTIVE`/`COMPLETED` events newest first, each with `podium` (top 3 of `computeStandings`, incl. `ratingChange`), player count and live-match count. `userId` narrows to that player's events and then includes private ones. Backs the "Итоги" tab of `ResultsPage`.
- `GET /leaders?metric=rating|wins|played&period=month|year|all&city=` — "Лидеры" tab. `rating` is the net rating change (`eloDelta` for a win, `eloDeltaLoser` for a loss) over the window.
- `GET /players/:id/stats` — rating history (walked backwards from today's rating through `Match.eloDelta`/`eloDeltaLoser`, so it needs nothing else stored), form (last 10), streaks, match/set/deciding-set rates (a decider = final tally one apart with the loser on at least one set), best win, nemesis/favourite opponent (2+ meetings), placings in finished tournaments of 3+ players, and achievements (computed live, never stored). Rendered by `components/PlayerStats.tsx` on `ProfilePage` and `PlayerPage`.
- `GET /players/:id/h2h/:otherId` — head-to-head; `HeadToHead` in the same component, on `PlayerPage` (signed in, someone else) and compact on `MatchPage` before a match starts.
- `Match.rating1Before`/`rating2Before` are snapshotted by `finishMatch` so "best win" / the 100+ achievement judge the opponent's rating at the time. Older matches have them null and simply don't count for those two.
- Standings rows carry `ratingChange` (net rating change in that event); `TournamentPage` shows it and each match row shows the winner's gain and the loser's loss.

**Editing your own profile**: `PUT /players/:id` (owner, or an `ADMIN` editing someone else) takes `UpdateProfileSchema` — `firstName`, `lastName`, `email`, `club`, `city`, `phone`, `dateOfBirth`, plus `currentPassword`+`newPassword` for a password change. Only the fields actually sent are written, so a form submitting one change doesn't blank the rest. Two fields are deliberately **not** settable: `rating`, because it is Elo computed from settled matches and posting it would make the ladder meaningless (the edit form shows it as a read-only line saying so), and `role`, which would be a free promotion to `ADMIN`. A password change by the owner requires the current password; a duplicate `email` comes back as a friendly 400 rather than a Prisma `P2002`. The route answers with the same shape as `/auth/me`, so `ProfilePage.tsx` drops it straight into the session user.

**The session user goes stale, and the rating is what shows it.** `AuthContext` fetches `/auth/me` once when the token is set, so `user.rating` — rendered in the header `Avatar` and on `ProfilePage` — was whatever it was when the app was opened, while Elo moves it after every settled match. The context therefore exposes `refreshUser()` (re-reads `/auth/me`) and `setUser()` (for a screen handed a fresh copy), re-reads on window focus/visibility change, and `ProfilePage` calls `refreshUser()` on mount. Any new screen that displays something the server can change underneath it should do the same rather than trusting the session copy.

**Player profiles**: `GET /players/:id` (auth required, `server/src/routes/players.ts`) returns the player's public fields, their last 25 completed matches with opponent/event/sets, and a win-loss count over those matches. It backs `/player/:id` (`PlayerPage.tsx`) and the match history on `ProfilePage.tsx`. Every place a player is listed — the rating table, a roster row, a standings row, the bye line — links there; before this, tapping a player did nothing anywhere in the app.

**`/players` and `/rating` are one screen.** They used to be two components rendering the same rows with a different sort. `RatingPage.tsx` is the surviving list (rating order, search, medals for the top three, each row linking to the profile) and `PlayersPage.tsx` is a one-line re-export so the older route keeps working; the Dashboard tile points at `/rating`.

No emoji anywhere in UI copy or code comments.

`client/src/components/Layout.tsx` provides a fixed bottom tab bar — **5 items** for a signed-in user: Home, Play (`/bookings`), Rating, Results, Profile (a guest gets `GUEST_NAV` instead, see Guest mode below) (`/players` is no longer a bottom-tab destination; it's a quick-action tile on `Dashboard.tsx` instead) — plus a slim sticky top header showing the current user's `Avatar` (links to `/profile`) and a logout button. This is the app's only navigation chrome; new authenticated pages should render inside `<Layout>`. Unauthenticated/full-screen pages (`MatchPage`, `LiveScore`, `PublicTournament`, `Login`, `Register`, `TournamentChatPage`) render standalone without `Layout`.

`client/src/components/Avatar.tsx` (initials circle + a `#ccff00` rating-number badge overlapping the bottom-right corner, `size: "sm" | "md" | "lg"`) is the standard way to represent a player anywhere in the UI — used in `Layout`'s header, `PlayersPage`, `RatingPage`, `ProfilePage`, and participant/standings rows in `TournamentPage`. Reach for it instead of a bare name string when a player is shown in a list. `client/src/components/Logo.tsx` (`as: "link" | "plain"`, `size: "sm" | "lg"`) is the other shared visual atom, used in `Layout`'s header and the `Login`/`Register` hero.

**All UI copy goes through i18n** (`client/src/i18n/index.tsx`): `const { t, lang, setLang } = useT()` and `t("some.key")`, never a hard-coded string in JSX. The dictionary is a flat `key -> string` map with `ru` and `en` sides; `ru` is the default and the product language, `en` is the fallback for any key missing from `ru`. `{placeholder}` interpolation is supported (`t("tournament.round", { n: 3 })`). The chosen language persists in `localStorage` under `lang` and is switched from the card at the bottom of `ProfilePage`. Dates go through `client/src/lib/format.ts` (`formatEventDay`, `formatTimeRange`, `formatSlot`), which takes `lang` and uses `Intl` — don't format dates inline.

**Player names always carry the surname's initial**: render them through `playerName(p)` from `client/src/lib/format.ts`, which produces `"Иван П."`. Scoreboards, match rows and results used to print the bare `firstName`, which made two players with the same first name indistinguishable. Roster and participant lists that show the full `firstName lastName` are left as-is — the surname is already there. Don't inline `p.firstName` in new UI.

Class strings several screens share live in `client/src/lib/ui.ts` (`field` for inputs/selects, `fieldLabel` for the caption above one), and the All/Mine feed switch is `components/ScopeToggle.tsx`; use them rather than pasting the string again.

When adding screens, reuse the existing hex values/spacing and the terse one-line JSX style already used in `pages/*.tsx` (inline conditional rendering, no per-row sub-components) rather than introducing new patterns.

## Repo layout — one API, two ways to run it

There is **one implementation of the API**, in `server/src`. Two entry points expose it:

- **`server/src/app.ts`** exports `createApp({ defaultClientUrl? })`, which builds the whole Express app: helmet, CORS, the JSON body limit, both rate limits, every router mounted under `/api`, `/api/health`, and the final error handler. Change routes, middleware and mounts **here and in `routes/`, once**.
- **`server/src/index.ts`** is the standalone process: loads `.env`, checks `JWT_SECRET` and the database connection, and `listen()`s. This is what runs locally (`npm run dev`), on Render (`render.yaml`) and in Docker. It passes `defaultClientUrl: "http://localhost:5173"`, the CORS origin used when `CLIENT_URL` is unset.
- **`api/index.ts`** is the Vercel serverless entry, three lines: `export default createApp()`. Vercel serves the client from the same origin, so with no `CLIENT_URL` it allows no cross-origin callers at all. Do not put logic in this file. (It used to be a 1700-line hand-copied duplicate of every route, which had already drifted from `server/`; the drift is what removing it fixed.)

Things to keep in mind because two runtimes load the same code:
- **No `.js` suffix on relative imports** in `server/src`. The standalone build (`tsc`) does not need one and Vercel's bundler resolves the extensionless `.ts` form reliably.
- The **root `tsconfig.json` is what Vercel type-checks `api/` with**, and it must stay `strict: true` like `server/tsconfig.json`; the server code does not type-check without it.
- Nothing may read an environment variable or open a connection at import time in a way that fails on one host and not the other (that is why `JWT_SECRET` is read lazily). Anything the standalone process needs at boot goes in `index.ts`, not `app.ts`.
- Prisma selects/includes and filters used by more than one route live in `server/src/shared/queries.ts` (`playerSelect`, `matchInclude`, `feedInclude`, `standingsInclude`, `inCity`, ...). Add to it rather than declaring a local copy: two locals that drift apart mean two endpoints returning the same object with different fields.
- `routes/setup.ts` (`GET /api/setup`) is the raw-SQL "create the tables" endpoint, kept for Vercel where nobody can run a migration. It is an old, partial DDL and is **not** the schema of record; it answers 404 unless `SETUP_KEY` is set.

Keep **both** hand-maintained SQL files in sync with `schema.prisma` if you change the schema. Neither is a real Prisma migration:

- **`server/prisma/migration.sql` — the one to run.** Additive and idempotent: it only creates tables/columns/indexes/foreign keys that are missing, each guarded by `IF NOT EXISTS` or an `EXCEPTION WHEN duplicate_object` block, so re-running it is harmless and **no data is lost**. It brings a database up to date from any earlier point. The single exception is the legacy free-text `Booking.club`/`Subscription.club` columns, which it migrates onto real `Club` rows before dropping — and that whole branch is skipped on a database that never had them. When you add a table or column, add it here as `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`.
- **`server/prisma/migration-reset.sql` — deliberate clean slate.** Drops every application table and recreates them empty. Running it always costs all existing data, so only reach for it when that is the actual intent. Add new tables/columns to its `CREATE TABLE` statements rather than appending `ALTER TABLE` sections.

After a reset, the seed (`npx tsx server/prisma/seed.ts`) is convenient for sample players but no longer required to get in: `POST /auth/register` is open self-signup. If unsure which database the user means, ask.

- `client/` — React 18 + Vite + Tailwind v4 + React Router SPA.
- The old `shared/` package, `server/src/services/` and `client/src/pages/BracketPage.tsx` (leftovers of the bracket/round-robin system) have been deleted. `server/src/shared/scheduler.ts` holds `generateRoundPairings` (the Swiss pairing/bye logic used by `POST /tournaments/:id/pair`); `server/src/socket.ts` is the unused Socket.IO layer (see Architecture notes).
- `public/` — pre-built static client assets committed for the Vercel static output fallback; not source, don't hand-edit.

## Commands

Run from the repo root (npm workspaces: `client`, `server`).

```bash
npm run dev              # runs server (tsx watch) and client (vite) concurrently
npm run build             # builds client only (npm run build -w client)
npm run db:push           # prisma db push against server/prisma/schema.prisma
```

Per-workspace (run with `-w server` / `-w client`, or `cd` into the folder):

```bash

npm run build -w server    # tsc -> server/dist
npm run dev -w client       # vite dev server (port 5173, proxies /api and /socket.io to :3000)
npm run build -w client     # vite build -> client/dist
```

Prisma (schema lives at `server/prisma/schema.prisma`):

```bash
npx prisma generate --schema=server/prisma/schema.prisma
npx prisma db push --schema=server/prisma/schema.prisma
npx tsx server/prisma/seed.ts     # seeds admin@localhost / organizer@localhost / sample players (all password: admin123)
```

There is no test suite and no linter configured in this repo. `server/.env` holds `DATABASE_URL`/`JWT_SECRET` for local runs — it's gitignored; check it exists before assuming `npm run dev -w server` or `db:push` will work, and note that **this sandboxed environment cannot reach outbound Postgres ports (5432)** even when a valid `DATABASE_URL` is configured — `prisma db push`/`db:connect` will hang or fail here regardless of credentials. That's an environment limitation, not a schema or credentials problem; it has to be run from a machine/CI with real network egress.

### Local DB via Docker

`docker-compose.yml` brings up Postgres (`tttournament` db, `postgres`/`postgres`) plus the app itself built from the root `Dockerfile` (multi-stage: builds `server` and `client` separately, then runs `node dist/index.js` serving the compiled server with the client build copied alongside).

### Deployment

- **Vercel** (`vercel.json`): builds via `prisma generate && npm run build -w client`, serves `client/dist` as static output, rewrites `/api/*` to the `api/index.ts` serverless function (which wraps `createApp()`, see Repo layout).
- **Render** (`render.yaml`): builds and runs the real `server/` (`tsc` then `node server/dist/index.js`), frankfurt region, expects `DATABASE_URL` set manually in the dashboard, generates `JWT_SECRET`.

## Architecture notes

**Auth**: JWT (`jsonwebtoken`), bearer token in `Authorization` header, secret from `JWT_SECRET` env var. There is **no fallback secret**: `server/src/index.ts` refuses to start without it, and on Vercel (which never runs that entry) every token operation fails instead: `jwtSecret()` reads it on use, so the public pages still serve. `/api/setup` answers 404 unless `SETUP_KEY` is set and passed as `?key=` or `x-setup-key`. Errors go through `publicError` (`server/src/shared/errors.ts`), which hides Prisma messages. Both deployments rate-limit: 1500 req/15 min overall (the scoring screen polls every 2s), 20/15 min on login/register. `GET /players` carries no email/phone. `server/src/middleware/auth.ts` exports `authMiddleware` (required auth) and `roleMiddleware(...roles)` (RBAC gate). **`roleMiddleware` is currently used by nothing.** `POST /auth/register` is open self-signup: it takes `SelfRegisterSchema` (no `role`, no `rating` — reading either from the body would let anyone sign up as an `ADMIN`) and creates an `ORGANIZER`, which only means "can run their own events" since per-tournament ownership is what actually gates anything. It used to require an already-authenticated `ADMIN`/`ORGANIZER` in `server/`, which meant the client's Register screen answered a brand-new user with a 401 on the Render deployment while the same screen worked on Vercel. Roles: `ADMIN`, `ORGANIZER`, `JUDGE`, `PLAYER`, `VIEWER`. Passwords hashed with bcryptjs.

**Polling, and why writes fight it**: `MatchPage`/`LiveScore` poll every 2s, `TournamentPage`/`PublicTournament` every 5s. On `MatchPage` the same screen is also being written to by the judge's taps, and a poll that overlaps a `/score` call returns a board without that set — applying it visibly rolls the score back, and a judge who sees their tap undone taps again. `MatchPage` therefore guards every mutation through a `write()` wrapper that tracks in-flight writes and a generation counter: it skips polling while a write is in flight and discards any poll response whose generation changed while it was on the wire. Keep new mutations inside `write()`.

**The scoring screen records sets.** `MatchPage` shows the set tally as the big numbers, two buttons that credit a set to a side, one undo, and "Завершить" as a full-width primary action — highlighted once `setsToWin` is reached, because nothing settles a match on its own and an unsettled match counts nowhere. Below the tally, a chip per set says who took it. There is no rally-by-rally board, no deuce indicator, no server line and no end-swapping: none of that is recorded.

**Destructive actions confirm in-place**: ending a match, a walkover and deleting a tournament all settle something that cannot be undone (`/end` also moves the rating), and on a phone held courtside they sit a thumb's width from the scoring buttons. Each renders an inline confirm panel rather than firing on the first tap — no `window.confirm`, same navy/lime styling as everything else.

**Real-time updates**: `server/src/socket.ts` holds a Socket.IO server, but it is **no longer initialized** — its `score-update`/`match-end` events changed matches with no authentication at all, bypassing every REST check. Wiring it back up means adding token auth and the same `loadScorableMatch` checks first. The **client does not use Socket.IO** — `client/src/context/SocketContext.tsx` (despite the filename) implements a `PollingProvider`/`usePoll` hook, and `MatchPage`/`LiveScore` poll their REST endpoints on a 2s interval instead. Treat the server's Socket.IO layer as unused by the current client unless wiring up real socket consumption.

**Guest mode**: browsing needs no account. `RequireAuth` (`client/src/App.tsx`, redirects to `/login` when `AuthContext` has no token) now wraps only the screens that *write* something — `/bookings`, `/profile`, `/tournament/new`, `/tournament/:id/chat`. Everything else reads: the feed (`/`), the rating list (`/rating`, `/players`), a player's profile (`/player/:id`), results, games, an event page and a match page, plus the already-public `/public/tournament/:id` and `/live/:tournamentId`.

A guest is view-only, and that is enforced in three places rather than by hiding buttons alone:
- **Server**: `GET /players/:id` is unauthenticated (its select is the public shape — no email, no phone), because a guest tapping a name in the rating table has to land somewhere. `GET /players` keeps `authMiddleware` — it carries emails. Every other endpoint a guest screen calls was already unauthenticated; the gated GETs (`/auth/me`, `/players`, `/profile/stats`, `/tournaments/mine`, `/tournaments/:id/chat`, `/bookings/mine`, `/subscriptions/mine`) are exactly the ones no guest screen requests.
- **Client fetches**: a screen that a guest can open must not fire a gated request. `TournamentPage` skips `players.getAll()` when there is no token, and the All/Mine toggles on `Dashboard`/`GamesPage` fall back to the open feed.
- **Client actions**: "Подать заявку", the create/edit/pair/delete controls and the chat link are replaced for a guest by a link to `/login` (`guest.signInToJoin`) or simply absent. The write endpoints behind them all require auth anyway — the UI just stops offering a door that is locked.

`Layout` swaps the header avatar for a "Войти" button and uses a different bottom bar for guests (`GUEST_NAV`: Home, Games, Rating, Results, Sign in — no Play, no Profile, since neither works without an account). `Login` offers "Продолжить без входа", which is how someone gets into guest mode deliberately rather than by accident. `client/src/services/api.ts` centralizes all REST calls through an `apiService` object backed by an axios instance that auto-attaches the JWT from `localStorage`.

**Demo mode: a throwaway account, not a fake one.** Browsing tells a newcomer nothing about what the app is for — pairing a room and recording sets is invisible until you do it — so "Попробовать демо" (`POST /auth/demo`, unauthenticated, on `Login` and the guest hero of `Dashboard`) signs the visitor in as a real account that already owns a `DRAFT` event with one sparring partner on the roster — two players, "Гость 1" and "Гость 2", which is the shortest complete evening there is: one pair, one match to score and settle. It is a starting point, not a cap: `maxPlayers` is unset, so the demo event takes more players and more matches like any other, and drops them on it. They pair it, score their own match, settle it and read the table exactly as a manager does, because it *is* the manager flow — there is no second, simplified copy of any screen to keep in step.

- `server/src/shared/demo.ts` owns all of it: `createDemoAccount()` (guest + opponent + event in one **batch** `$transaction([...])` — the interactive form holds a session open across round trips and a connection pooler in front of Postgres does not survive it; ids are generated up front so the roster needs no read-back), `sweepExpiredDemos()` and the `notDemo` filter.
- `User.isDemo`/`demoOwnerId`/`demoExpiresAt` carry it. Demo rows are excluded from the rating list and `GET /players` (`notDemo`) and from `/leaders` (`player1`/`player2`), and the event is `isPublic: false`, which keeps it out of the feed and `/results`. **Any new list of players or matches has to exclude them too** — a sparring partner is not a person and must never appear next to real players.
- **Expiry and cleanup**: an unclaimed set lives `DEMO_TTL_HOURS` (24) and is then deleted whole — user rows, event, matches, sets. The sweep runs opportunistically at the start of `POST /auth/demo` rather than on a schedule, because neither deployment target has a scheduler and demos can only pile up while demos are being created. Nothing cascades, so it deletes in the same hand-written order `DELETE /tournaments/:id` uses.
- **Invitation link**: a demo has one sparring seat, and it can be handed to a real person. `POST /auth/demo/join { tournamentId }` (unauthenticated, `joinDemoSeat` in `demo.ts`) creates a second guest account (`isDemo`, `demoOwnerId` = the manager, expiring with them) and *moves* the sparring partner's seat to it: the `TournamentUser` row, any match already paired and the round bye now point at the guest, who keeps the partner's rating. The sparring partner is deleted. One seat, one taker: a second redeemer gets 409, an expired or non-demo event 404/410. The seat counts as open while a roster member is still a demo user whose email starts with `demo-` (guests get `guest-`), which is how `GET /tournaments/:id` computes `demoSeatOpen` without a schema change. The manager's `TournamentPage` shows the link (`/demo/join/:id`) while the seat is open; `DemoJoin.tsx` is the landing page (joining is an explicit tap, so a link preview cannot use the seat up) and skips the tour for the guest. Both players then open the same match and either can score it, because scoring is open to both players of a match.
- **Claiming keeps the same row**: `POST /auth/claim` (auth, `ClaimDemoSchema`) sets the visitor's real email/password/name, clears `isDemo` and `demoExpiresAt`, and clears the expiry on the opponents (which stay `isDemo`, so they never enter the ladder, but must not be swept out from under the matches). That is the whole reason the demo is a server account instead of a browser-side sandbox: signing up is an UPDATE, so the evening they just ran stays theirs — including the rating those matches moved.
- **The tour** is `client/src/lib/tour.ts` (a fixed step list plus a localStorage index, deliberately outside React so a page advances it with a one-liner) and `components/Tour.tsx`, mounted once in `App.tsx` so it follows the visitor onto `MatchPage`, which renders outside `Layout`. Every step points at a `data-tour="..."` anchor on a real screen and rings it rather than covering the page — the visitor has to be able to tap the button being described. **A step without an anchor is not a step**: when its control is not on screen the card shows that step's `wait` copy ("the pairing button is below the roster") and hides "next", so the tour can never walk past the one thing it is about. A step with `doneBy` advances itself when the screen reports that action (`tourDone("pair")`), so nobody confirms something they have just done. A step with `press` makes "Next" *press the real control* (`pressStep` in `tour.ts` clicks the anchor: pairing, opening the match, starting it, tapping sets for the visitor's side until the match's `setsToWin` is reached, then "end" and its in-place confirm), so the screen's own handler runs and reports `tourDone` — without it "Next" on the pairing step skipped the one button the step is about and nothing was ever paired. The "record sets" step completes when a side reaches `setsToWin`, not on the first set. It only renders for `user.isDemo`. `components/DemoBanner.tsx` (in `Layout`) is the standing "this is temporary" strip and holds the claim form — the only copy of it, which screens open through `requestClaim()` in `lib/tour.ts`. `TournamentPage`'s "add players" button does exactly that for a demo manager instead of opening the roster picker: adding *real* people to a throwaway event would put it in their history, so that button is where the offer of a real account belongs.

**Validation**: Zod schemas for request bodies live in `server/src/shared/schemas.ts` (used by `server/src/routes/*`) — the top-level `shared/schemas.ts` package is a separate, unused leftover (see dead-code note above).
